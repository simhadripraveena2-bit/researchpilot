| File | What it is | Who edits it |
|---|---|---|
| `G_MATCH_B0_REVIEW.md`, `G_LATEST_DATES_B0_REVIEW.md` | One entry per case: AI-proposed label, expected system behaviour, explanation, cited evidence, the original recorded source records (with file paths), known ambiguities and missing evidence, review status | Generated by `backend/scripts/b0_review_sheets.py`; never by hand |
| `g_match_b0_decisions.csv`, `g_latest_dates_b0_decisions.csv` | One row per case. The reviewer fields start blank. | The reviewer |

The generator creates each decisions CSV once and never overwrites it. CI fails if a sheet is
stale (`tests/unit/test_review_sheets.py`) and rejects unknown case IDs or decision values.

## Who reviews

B0 may be reviewed by a **team member** (EVALUATION_FRAMEWORK §2a, §2b), not the AI assistant
that proposed the labels. The reviewer is named by handle in the CSV. Expert adjudication is
not required for B0, and a reviewed B0 label is still not expert-validated.

## How to review a case

1. Read the sheet entry. Treat the recorded responses as **what the system saw**, not as the
   truth.
2. Open the primary pages:
   - arXiv abstract page and submission history; for announcement dates, the listing
     (`arxiv.org/list/<cat>/...`);
   - the bioRxiv/medRxiv page and its posting history;
   - the publisher landing page (online / issue dates, the article itself).
3. Decide the **ground truth** first (same work / related / different; the true first public
   date), then whether the **expected system behaviour** follows from the guideline and the
   evidence the system can see. Notes marked "TRUTH vs POLICY" flag cases where these
   differ by design.
4. Fill in the row:

| Column | Content |
|---|---|
| `reviewer` | Your handle |
| `decision` | `confirm`, `correct` (give the corrected label), `reject_case` (unusable: wrong records, unverifiable) or `unsure` (needs the evaluation lead) |
| `corrected_label` | Only for `correct`, in the same form as `ai_proposed_label` |
| `reason` | One or two sentences |
| `evidence_checked` | URLs of the primary pages you opened |
| `review_date` | ISO date |

5. Do **not** run the system or look at its output while deciding. The B0 reports show
   system output, so review before reading them (or treat them as unseen).

## How a reviewed label enters the dataset

Labels are never changed automatically. After a decision:

1. A person edits `backend/benchmarks/build_b0.py`:
   - `confirm`: set the case's `labels.status` to `team_reviewed`, and set `annotators` and
     `approved_by` (if the evaluation lead approves) to the reviewer's handle;
   - `correct`: change the expectation and explanation, then set the status as for
     `confirm`;
   - `reject_case`: remove the case. Its ID is never reused.
2. Regenerate the data and sheets:
   ```bash
   uv run python benchmarks/build_b0.py
   ```
   ```bash
   uv run python scripts/b0_review_sheets.py
   ```
3. Run the B0 benchmark. If the system now disagrees with a corrected label, that is a
   finding to report, not a reason to change the label back.
4. Commit with the reviewer named in the commit message.
